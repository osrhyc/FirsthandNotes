# 一手笔记整体设计

> 当前实现基线：2026-07-27
>
> Slogan：记录值得长期保存的知识

## 1. 产品定位

一手笔记是一个以 Markdown 为长期数据源的个人知识站。它不追求收集尽可能多的信息，而是把经过研究、完整阅读和持续筛选的内容整理成可以长期回看的知识。

当前包含三个主要内容模块：

| 模块 | 用途 | 内容入口 |
| --- | --- | --- |
| 博客 | 学习文档、内容拆解、人物与行业事件等长期文章 | `/` |
| 书籍 | 基于用户提供原书的逐章精读笔记 | `/books/` |
| 每日简报 | 技术、商业、创业、营销、金融、股市和基金信息 | `/briefings/` |

名词手册是文章阅读中的辅助能力，暂不作为独立的一级产品。

## 2. 已确定的体验

### 2.1 首页

首页保持 Fuwari 的文章流，展示普通博客文章。书籍章节、每日简报和名词解释不混入首页文章列表，避免高频内容淹没长期文章。

### 2.2 书籍

书籍是独立模块：

- 书籍首页展示最近更新的章节，而不是最近更新的书。
- 全部书籍按分类平铺展示，分类默认展开。
- 分类筛选使用符合站点风格的自定义弹层，不使用浏览器原生下拉框。
- 点击书籍后直接进入章节阅读，不增加中间目录页。
- 阅读页左侧固定为该书章节目录，中间为正文，右侧保留文章页目录。
- 当前章节必须高亮，并支持快速切换其他章节。

### 2.3 每日简报

每日简报是独立模块：

- `/briefings/` 展示最新一期和历史简报。
- 简报阅读页左侧为日期归档，中间为正文，右侧保留文章页目录。
- 简报不进入首页文章流和普通文章分类统计。
- 内容覆盖 AI、开发、创业、营销、商业、金融、股市、基金，并可根据当天重要性动态调整。

## 3. 当前技术架构

技术基座为 Astro 5 + Fuwari + Markdown，输出纯静态页面并由 GitHub Pages 托管。无需数据库、CMS、后端服务或常驻运行时。

### 3.1 内容源

```text
src/content/blog/       普通文章与每日简报
src/content/books/      逐章书籍笔记
src/content/glossary/   名词解释
src/content/spec/       站点说明类内容
```

这些目录是内容的唯一长期数据源。构建前，`scripts/sync-fuwari-content.mjs` 将不同内容统一投影到忽略提交的 `.generated/`：

```text
.generated/posts/              Fuwari 文章集合
.generated/books.json          书籍与章节索引
.generated/briefings.json      简报日期索引
.generated/post-summary.json   普通文章分类与标签统计
```

Astro 当前只需要读取生成后的 `posts` Collection。书籍和简报的独立体验由生成索引及专用页面实现，不为追求形式上的“模块独立”拆成四个 Content Collection。

### 3.2 当前路由

```text
/                         普通文章首页
/posts/[slug]/            普通文章、书籍章节和简报正文
/books/                   书籍首页
/briefings/               每日简报首页
/archive/                 归档
/about/                   关于
/rss.xml                  RSS
```

保留统一的 `/posts/[slug]/` 正文路由可以复用 Fuwari 的 Markdown、代码块、目录、搜索和 SEO 能力。只有出现明确的 SEO 或信息架构收益时，才迁移到更深的模块路由。

### 3.3 构建与发布

```text
Markdown 源文件
  -> 内容同步与索引生成
  -> Astro 静态构建
  -> Pagefind 搜索索引
  -> dist/
  -> GitHub Actions
  -> GitHub Pages
```

本地命令：

```bash
npm run check
npm run build
npm run dev -- --port 4321
```

普通文章和书籍笔记先在本地构建、预览并由用户确认，再提交或推送。GitHub Pages 工作流只负责在 `main` 更新后重新构建和发布。

## 4. 写作与阅读 Agent

`.ai/` 是跨工具规则的唯一事实来源：

| 工作流 | 共享规则 | 用途 |
| --- | --- | --- |
| 研究型写作 | `.ai/writing-agent.md` | 技能文档、内容拆解、人物行业、大事件等 |
| 真读精读 | `.ai/read-book.md` | 基于用户提供 PDF/EPUB 的完整逐章精读 |
| 每日简报 | `.ai/daily-briefing.md` | 每日联网检索、筛选、去重、写作与发布 |

工具专属入口保持轻量，只负责指向共享规则：

- Codex：`AGENTS.md`
- Claude Code：`.claude/commands/write-article.md`、`.claude/commands/read-book.md`
- Cursor：`.cursor/rules/writing-agent.mdc`、`.cursor/rules/read-book.mdc`

书籍精读不能使用网络书评、摘要或模型记忆代替原书。普通文章可以联网研究，但必须区分事实、观点、传闻和推断，并在相关事实旁保留来源。

## 5. 每日简报自动化

每日简报由 ChatGPT 的定时任务在每天 10:00（Asia/Shanghai）触发，不使用 n8n。

```text
ChatGPT 定时任务
  -> 搜索过去 24 小时及持续发酵的重要信息
  -> 来源分级、交叉验证、与近期简报去重
  -> 生成 src/content/blog/daily-briefing-YYYY-MM-DD.md
  -> 内容检查与构建
  -> 提交并推送 GitHub
  -> GitHub Actions 发布
```

该自动化只获得“每日简报”范围内的定时发布授权。普通文章和书籍笔记仍执行本地预览后由用户明确批准发布的流程。检索规则、内容结构和失败处理见 `.ai/daily-briefing.md`。

## 6. 视觉基线

- Fuwari 是站点 UI 与阅读体验的基础，不再混入管理后台、Starlight 或其他主题体系。
- 品牌使用藏青、金色和暖白，Logo 由书本、笔尖和书签构成。
- Slogan 与导航栏 Logo 一起展示，不保留独立品牌介绍卡片。
- 各模块共享排版、卡片、明暗主题和响应式规则，仅通过图标和少量信息结构体现差异。
- 优先保证正文宽度、字体大小、章节切换和移动端阅读，不为装饰覆盖大量 Fuwari 变量。

## 7. 质量与权限

- 外部事实必须有可访问的来源链接。
- 争议内容必须区分已确认事实、单方说法、传闻和编辑推断。
- 精读笔记必须可追溯到原书阅读单元，原书和提取文本永不入库。
- 自动化校验失败时不得强行发布，应保留草稿并报告失败原因。
- 每次代码或规则改动都要提交独立 commit；除已授权的每日简报任务外，不自动推送。

## 8. 与旧方案的差异

以下内容不再作为当前实施目标：

- 不使用 n8n，定时工作由 ChatGPT 任务承担。
- 简报发布时间不是 11:00，而是每天 10:00。
- 不建立 `posts / books / bookNotes / briefings` 四个独立 Collection。
- 不将首页改造成包含所有模块的仪表盘。
- 不新增书籍详情中间页，书籍首页直接进入章节阅读。
- 不要求 `/blog/`、`/books/[book]/notes/[note]/`、日期型简报路由；当前统一文章路由已满足使用需求。
- 不引入 Ant Design、React SPA、数据库或传统 CMS。
- 不先建设 PRD、ADR、Task、Log 的完整文档体系；只在复杂决策确有维护价值时增加。

## 9. 后续更新优先级

1. 完善内容校验：重复 slug、重复简报日期、失效内部链接和缺失来源。
2. 为 Pagefind 搜索结果增加模块标识或过滤能力。
3. 按需增加分模块 RSS。
4. 为文章和简报补充更准确的结构化数据与分享图。
5. 当现有统一正文路由造成实际问题时，再评估模块化 URL 迁移。
